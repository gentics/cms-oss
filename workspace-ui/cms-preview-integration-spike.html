CMS Preview Integration Spike

As of 2026-10-08 · Gentics Workspace UI · GenAIx contract 1.0.0-rc.2

Recommended: frame a read-only CMS rendering in a same-origin iframe, draw selection in an overlay owned by the Workspace, and route edits through GenAIx. Showing the page works with the CMS as it is. One blocker remains on the GenAIx side: it must accept a reference to one element. Element markers need either a CMS setting or a small CMS change.

The Workspace UI runs on the same server as the CMS (served at /workspace/); GenAIx is a separate product with its own contract. Everything here was read from code and contracts. Nothing was run against a live CMS; the one-day prototype at the end validates the runtime parts.

Recommended architecture

The iframe loads the page with the user's own CMS session; the overlay reads its tag markers through same-origin access; every content change is written by GenAIx and comes back as preview.updated. Two arrows depend on open items: the markers the overlay reads (question 4) and a tag reference in the message (question 1).

1. Framing and embedding

Recommendation: the Workspace builds the iframe link itself from cms_ref in preview.updated: /alohapage?real=newview&realid=<id>&nodeid=<node_id>. GenAIx's preview_url is only used for an "Open" link beside the frame, as the integration guide asks.

OptionWhat it rendersLockAloha scriptsVerdict

GET /rest/page/render/content/{id}Raw HTML in EM_PREVIEWNoNoFallback; fewer markers

Why same-origin works: /workspace/*, /alohapage and /rest/* are registered on one Jetty context, and the GCN_SESSION_SECRET cookie is set with path /, so the iframe loads with the user's own session. No CMS code sets X-Frame-Options or frame-ancestors; a proxy in front of the CMS might, which Ops has to confirm.

Why we don't frame preview_url: GenAIx sends alohapage?realid=9142&nodeid=3&mode=view, but AlohaPageServlet has no mode parameter. Without real=view|newview it renders edit mode, locks the page for a user with edit permission, and loads Aloha scripts that call window.parent.GCMSUI_childIFrameInit, which only the editor UI defines. The servlet is also @Deprecated in favour of the REST render endpoint. cms_ref requires only type and id; when node_id is missing, the session's node is the fallback (our proposal).

Limits:

  • Same-origin and unsandboxed, the customer's template JavaScript runs with access to the Workspace. A sandbox without allow-same-origin would protect us but also block the overlay.
  • Every preview.updated reloads the iframe. Same-origin lets us save and restore the scroll position; loading into a hidden second iframe and swapping would avoid a flash (not tested).
  • Mobile view = the iframe set to 390 px wide, so the page's own media queries apply.

2. Identifying elements

Recommendation: validate the COPY_TAGS feature first, since it needs no code change. If it does not fit and we can change the CMS, add a read-only rendering with markers.

What the CMS renders (AlohaRenderer):

  • Edit mode wraps every editable block with class="aloha-block", id="GENTICS_BLOCK_<tagId>" and data-gcn-pageid, data-gcn-tagid, data-gcn-tagname, data-gcn-i18n-constructname.
  • Read-only and preview add those attributes only to inherited template tags, or to every tag when the COPY_TAGS feature is on for the node. A normal read-only preview gives us nothing to find content tags by.
  • changed_elements in preview.updated holds tag keywords such as content_1. We expect these to equal data-gcn-tagname; this is not verified.

3. Overlay-based selection

Recommendation: the Workspace draws outlines, labels and dimming in its own layer above the iframe and never changes the customer's DOM.

  1. After each load, query the iframe's contentDocument for [data-gcn-tagid] and read each element's getBoundingClientRect.
  2. Position outline boxes in an overlay stacked over the iframe; recompute on scroll, resize, reload and DOM changes (ResizeObserver, MutationObserver).
  3. Hover highlights only the deepest tag under the pointer; a click selects and opens the element menu with only the allowed actions.
  4. States per tag: selected, changed (from changed_elements), locked, and, if GenAIx confirms, busy and failed from the page_structure block status (planned, created, updated, locked, failed).
  5. Focus mode = an overlay mask with a cut-out around the target.

Limits:

  • A selection stays a UI concept: ContextReference has no tag type, so it cannot be sent to GenAIx yet.
  • Clicks inside an iframe are not keyboard-accessible. A tag list beside the frame (GET /rest/page/getTags/{id}) gives keyboard users the same selection, with Alt+Up/Down for parent and child as in the mockup.
  • The overlay needs same-origin access; a cross-origin preview would rule this approach out.

4. Lock state

Recommendation: show one page-level lock banner and disable edit actions while someone else holds the lock; mark template tags as "from the template" per tag.

FactSource

How the UI shows it:

  • Read the lock with a plain page load (never update=true, which takes the lock) when the preview opens; refresh it on preview.updated and on any 423.
  • Banner: "<user> is editing this page since <time>"; feedback and edit actions disabled.
  • Per tag, only "from the template" is detectable (Tag.type = TEMPLATETAG / inherited).

Not possible: the mockup's per-element "M. Weber is editing this", because the CMS locks whole pages. Without a CMS change also not possible: a "from the data source" lock (no source found) and "Ask for the lock" / "Leave a note" (no API found).

The contracts state "one write path" through the CMS REST API but do not say whether the Workspace UI may write page content itself during a session; that is question 6 below.

Edit a text with GenAIx

The user selects an element and says in the chat what should change; GenAIx writes the change, it is saved at once as an unpublished version, and the preview reloads with the change highlighted.

  1. Select: the user clicks the element in the overlay (or picks it from the tag list).
  2. Describe: the user types the change in the chat, e.g. "Make the headline shorter". The element goes along as a reference, once GenAIx supports a tag reference (question 1); until then the user names it in words.
  3. GenAIx works: a run starts. GenAIx may ask back through an interaction card (question, choice, confirmation), and before its first CMS write in a run it can show a settings review to confirm.
  4. Saved: GenAIx writes with update_page_tags; the change is saved immediately as an unpublished version.
  5. Shown: preview.updated arrives with changed_elements; the frame reloads and the overlay highlights the changed element.
  6. Next: not happy → ask again, or use "Edit by hand"; done → Publish.

Edit by hand in the page

For users who want to type directly in the page, like in the mockup: a separate "Edit by hand" mode that switches the frame to the CMS's own edit mode while no AI run is active.

  1. The user clicks "Edit by hand". It is only offered while no AI run is active (run.started / run.completed on the stream); a running run can be stopped first with POST /sessions/{session_id}/runs/{run_id}/cancel. GenAIx has no "pause".
  2. The frame switches to /alohapage?real=newedit&realid=…&nodeid=…: the CMS's edit mode (Aloha), as the CMS editor uses it.
  3. The user types directly in the page and clicks Apply (saves via the page's save function inside the frame, as the CMS editor does) or Cancel (drops the unsaved text).
  4. The frame goes back to read-only, the chat shows a note such as "@Headline — written by hand", and the AI can continue.

When changes are saved

Every change is saved in the CMS the moment GenAIx writes it; there is no separate save step. Going live is a separate step: the publish transition.

  1. New page: created at the start as an offline draft; create_page never publishes (mcp-tools.json, create_page).
  2. Each content change: saved by update_page_tags, which locks, applies, saves, creates a version and unlocks inside one call (mcp-tools.json, update_page_tags; 04-mcp-scope.md:325-328).
  3. Preview: preview.updated fires after every CMS write, so each reload shows something already saved.
  4. Publish: only through the publish transition; gates run first, and the CMS decides between direct publish and review request.

What that means for "Save", "Publish" and "Discard" buttons (the mockup has all three on its review screen):

ButtonMaps toWorks?
PublishTransition publishYes
SaveNothing to call, changes are already saved unpublished; or release to stop the AI and freeze the sessionYes, but not "save now"
DiscardTransition discard; it starts no run, and no source says it undoes CMS changes. With a CMS change, a restore to the version from before the session could be added.Unclear: question 3

Holding changes back until a click on "Save" would need GenAIx to stop writing directly: the preview always shows what the CMS has stored. Not covered by the sources: how many saves one AI step makes, and whether unpublished edits to an already published page stay off the live site until publish.

Open questions and dependencies

One item blocks implementation (1); the rest shape it.

  1. GenAIx — tag reference. Add a ContextReference for one tag on one page (page + tag keyword), so a selection can be sent with a message or a verbatim part.
  2. GenAIx — preview URL. Not blocking, because the Workspace builds its own frame link, but preview_url should be fixed for the "Open" link: mode=view opens edit mode and locks the page. When is mode: edit sent at all?
  3. GenAIx — discard. What does discard do to the CMS: delete a new draft page, restore the version from before the session, or nothing? Do unpublished edits to a published page stay off the live site until publish?
  4. CMS — markers. Is COPY_TAGS acceptable on the nodes we target (default, side effects), or do we need an annotated read-only rendering?
  5. Team — CMS changes. May the CMS be adapted for the Workspace? This decides the four points in "If we can change the CMS".
  6. Team — write path. May the Workspace UI write page content directly during a session, or only through GenAIx?
  7. Product — scope. Accept page-level locks instead of per-element locks, hand editing in a form instead of inline, and decide on per-suggestion Accept/Discard and on the CMS extras.
  8. GenAIx — states and pages. Can page_structure block status drive per-tag busy/failed/locked, and can the workflow snapshot hold one preview per page?
  9. Security — isolation. Is running the customer's template JavaScript same-origin and unsandboxed next to the Workspace acceptable?
  10. Ops — proxy. Does a proxy in front of the CMS add X-Frame-Options or CSP?
  11. Edit by hand — bridge. Does text editing work with the minimal bridge plus toolbar components, without the tag functions? Does its save write only the edited fields?
  12. GenAIx — hand edits. How should GenAIx learn about a hand edit, for example a follow-up message with the text as a verbatim part?

Next step: a one-day prototype

A throwaway page in the Workspace, served from /workspace/ against a real CMS, settles everything this spike could not verify from code.

  • Build the frame link from a real cms_ref and frame /alohapage?real=newview&realid=<id>&nodeid=<node>: does it render, and is contentDocument readable?
  • Confirm the page is not locked afterwards (locked on a plain page load).
  • Query [data-gcn-tagid] with COPY_TAGS off and on; count how many content tags are found.
  • Draw overlay outlines from getBoundingClientRect; check scroll, resize and a reload.
  • Compare a GenAIx changed_elements value with data-gcn-tagname on the same page.
  • Trigger a lock from a second user and check the banner data (lockedBy, lockedSince).
  • Repeat behind the production proxy to see whether framing headers appear.
  • Switch the frame to real=newedit with a stub GCMSUI_childIFrameInit: can the page be edited and saved, and do the toolbar components arrive through registerComponent?
