h2. Portal Implementations

Portal Implementations hold the files of a portal implementation (e.g. the Handlebars templates and GraphQL queries of a Java portal) inside the CMS.
They can be put into devtool packages, assigned to nodes and are published into Mesh ContentRepositories.

endprologue.

h3. Attributes

Every Portal Implementation has the following attributes:

|_. Attribute   |_. Description |
| id            | Local ID, generated by the database |
| globalId      | Global ID, generated by the database or given when the Portal Implementation is created. It cannot be changed afterwards |
| keyword       | Keyword identifying the Portal Implementation. Mandatory, must be unique, at most 255 characters |
| name          | Name of the Portal Implementation. Mandatory, must be unique, at most 255 characters |
| description   | Description |
| type          | Type of the Portal Implementation, either @PHP@ or @Java@. Mandatory |
| creator       | User who created the Portal Implementation (set automatically) |
| cdate         | Creation timestamp (set automatically) |
| editor        | User who edited the Portal Implementation last (set automatically) |
| edate         | Timestamp of the last edit (set automatically) |

Leading and trailing whitespace of keyword and name is removed. Trying to save a Portal Implementation with a keyword, name or globalId,
which is already used by another Portal Implementation fails with @409 Conflict@.

NOTE: The keyword is used as directory name, when the Portal Implementation is put into a "devtool package":#devtool-packages.
It should therefore only contain characters that are valid in directory names.

h3. Permissions

Permissions on Portal Implementations work like permissions on ContentRepositories:

|_. Level                                    |_. Permissions |
| Portal Implementations (the whole module)   | view, assign permissions, create |
| Single Portal Implementation                | view, assign permissions, edit, delete |

The module is visible to users having view permission on Portal Implementations (and permission to access the administration).
Changing the files of a Portal Implementation requires the permission to edit the Portal Implementation.

When updating to a CMS version containing Portal Implementations, every group gets the same permissions on Portal Implementations
it has on ContentRepositories. When a new Portal Implementation is created, the permissions are set like for newly created ContentRepositories.

h3. Administration UI

Portal Implementations are managed in the module _Portal Implementations_ of the administration UI. The module allows to

* list Portal Implementations (with search, sorting and paging)
* create, edit and delete Portal Implementations
* assign a Portal Implementation to nodes (action _Assign to Nodes_)
* list the files of a Portal Implementation (tab _Files_)

The files are read-only in the administration UI. Files are added, changed or deleted with the "REST API":#rest-api
or by synchronizing a "devtool package":#devtool-packages.

The assignment can also be changed in the node editor (tab _Portal Implementations_), and Portal Implementations can be added to
devtool packages in the package editor (tab _Portal Implementations_).

h3. Files and folders

A Portal Implementation contains files, which are organized in folders. Every file has a path (including the filename), e.g. @templates/contentpage.hbs@.

* Folders are not stored separately. A folder exists as long as it contains at least one file and is created implicitly, when a file is stored into it.
* Paths are case sensitive.
* A path must not be empty, must not be longer than 512 characters and must not contain backslashes or control characters.
  Every segment of the path must be non-empty, must not be @.@ or @..@ and must not start or end with whitespace.
* When storing a file without content type (or with @application/octet-stream@), the mimetype is detected from the filename and the contents.

The meta information of the files (path, mimetype, size, creator, creation date, editor and edit date) is stored in the database.
The file contents are stored in the folder @portalimplementations@ in the "dbfiles" folder of the CMS (configuration @DBFILES_PATH@,
default @data/dbfiles@), one file per Portal Implementation file.

Deleting a Portal Implementation also deletes all its files.

h3. REST API

All endpoints are relative to @/rest@. Portal Implementations are identified by their local ID or global ID.
The node and package endpoints additionally accept the keyword.

h4. Portal Implementations

|_. Method |_. Path                                         |_. Description |
| GET       | @/portalimplementations@                       | List Portal Implementations (supports filtering, sorting, paging and permission information) |
| POST      | @/portalimplementations@                       | Create a Portal Implementation |
| GET       | @/portalimplementations/{id}@                  | Load a Portal Implementation |
| PUT       | @/portalimplementations/{id}@                  | Update a Portal Implementation |
| DELETE    | @/portalimplementations/{id}@                  | Delete a Portal Implementation (including its files) |
| GET       | @/portalimplementations/{id}/nodes@            | List the nodes the Portal Implementation is assigned to |

Example for creating a Portal Implementation:

<shell>
POST /rest/portalimplementations
{
  "keyword" : "portal-java",
  "name" : "Java Portal",
  "description" : "Handlebars templates and GraphQL queries of the Java portal",
  "type" : "Java"
}
</shell>

h4. Files and folders

|_. Method |_. Path                                                |_. Description |
| GET       | @/portalimplementations/{id}/files@                   | List all files (supports filtering, sorting and paging) |
| GET       | @/portalimplementations/{id}/folders@                 | List the files and folders in the root folder |
| GET       | @/portalimplementations/{id}/folders/{path}@          | List the files and folders in the given folder |
| PUT       | @/portalimplementations/{id}/folders/{path}@          | Move (rename) the folder. The body contains the new @path@. All contained files are moved |
| DELETE    | @/portalimplementations/{id}/folders/{path}@          | Delete the folder with all contained files |
| GET       | @/portalimplementations/{id}/files/{path}@            | Load the meta information of a file |
| PUT       | @/portalimplementations/{id}/files/{path}@            | Change the meta information of a file. Only @path@ (to move or rename the file) and @mimetype@ can be changed |
| DELETE    | @/portalimplementations/{id}/files/{path}@            | Delete a file |
| GET       | @/portalimplementations/{id}/content/{path}@          | Get the file contents (with the mimetype of the file as content type) |
| PUT       | @/portalimplementations/{id}/content/{path}@          | Create or replace a file with the request body as contents. The content type of the request is used as mimetype |

Example for uploading a file:

<shell>
curl -X PUT -H "Content-Type: application/octet-stream" --data-binary @contentpage.hbs \
  "https://cms.example.com/rest/portalimplementations/1/content/templates/contentpage.hbs"
</shell>

Moving or creating files fails with @409 Conflict@, if the new path conflicts with existing files or folders.

h3. Assignment to nodes

Portal Implementations are assigned to nodes. A node can have several Portal Implementations and a Portal Implementation can be assigned to several nodes.

* Changing the assignment requires view permission on the node, the node permission to change the assigned tagtypes and view permission on the Portal Implementation.
* Channels always use the Portal Implementations of their master node. Changing the assignment for a channel (via the REST API) changes the assignment of the master node.
  The administration UI does not allow changing the assignment for channels.
* When a devtool package is assigned to a node, all Portal Implementations of the package are assigned to the node.
  Portal Implementations, which are added to the package later, are also assigned to the nodes the package is assigned to.
* Removing a package from a node does not remove the assignment of its Portal Implementations (like for tagtypes).

When a node or a Portal Implementation is deleted, the assignment is removed.

h3. Devtool packages

Portal Implementations (including all their files) can be put into "devtool packages":devtools_overview.html.
They are synchronized into the subdirectory @portal_implementations@ of the package, in a directory named after the keyword.
See "Directory layout":devtools_overview.html#portal-implementations for details.

h3. Publishing into Mesh ContentRepositories

Portal Implementations are published into "Mesh ContentRepositories":feature_mesh_contentrepository.html during the regular publish run,
right after the schemas and projects have been checked. They are not published by instant publishing.

h4. Schema

The publish process creates (or checks and repairs) the schema @[prefix]_implementation@ and assigns it to the projects. The schema contains the fields:

|_. Field       |_. Type   |_. Contents |
| keyword       | string   | Keyword of the Portal Implementation |
| name          | string   | Name of the Portal Implementation (display field) |
| description   | string   | Description of the Portal Implementation |
| package       | binary   | All files of the Portal Implementation as ZIP file (@[keyword].zip@), with the paths of the files |

The schema is not a container and is excluded from indexing.

h4. Nodes in Mesh

* All Portal Implementations assigned to a node are published as direct children of the root node of the node's Mesh project
  (in the branch, the node publishes into).
* The uuid of the Mesh node is derived from the uuid of the project and the global ID of the Portal Implementation,
  so the same Portal Implementation can be published into several projects.
* The Mesh nodes are published in the language @en@.
* A Portal Implementation is only written to Mesh, if it changed: the publish process compares the keyword, name, description and the SHA-512 checksum
  of the ZIP file with the data stored in Mesh. Unchanged Portal Implementations keep their version in Mesh.
* Portal Implementations, which are no longer assigned to a node publishing into the project and branch (or which were deleted), are removed from Mesh.
* Nodes, which have publishing disabled or do not publish into the ContentRepository, are ignored.

The "Check/Repair":feature_mesh_contentrepository.html of a Mesh ContentRepository also checks (and repairs) the published Portal Implementations.

h3. Using Portal Implementations in Portal | Java

Portal | Java can load its implementation (templates, queries, translations and static files) from a Portal Implementation published into Mesh,
instead of using only the files in its local @data@ folder.

h4. Configuration

The keyword of the Portal Implementation is configured with the setting @portalImplementation@ (or the environment variable @PORTAL_IMPLEMENTATION@):

<shell filename="config/server.yml">
meshProject: website
meshSchemaPrefix: website
portalImplementation: portal-java
</shell>

The portal looks for the Portal Implementation in the configured Mesh project, using the schema @[meshSchemaPrefix]_implementation@.
@meshSchemaPrefix@ must therefore match the schema prefix used by the Mesh ContentRepository the Portal Implementation is published into.
When @portalImplementation@ is not set, the portal only uses its local files.

h4. Loading the Portal Implementation

* When the portal is started, it loads the published node with the configured keyword, which is a direct child of the root node in the default branch of the project,
  and downloads the ZIP file of the @package@ field.
* The top level folders of the ZIP file are extracted into the configured folders, replacing their contents:

|_. Folder in the Portal Implementation |_. Extracted into                       |_. Default |
| @templates/@                          | @templatesPath@                        | @data/templates@ |
| @queries/@                            | @queryPath@                            | @data/queries@ |
| @i18n/@                               | @i18nPath@                             | @data/i18n@ |
| @static/@                             | @static.implementationPath@            | @data/implementation/static@ |

* Configured folders, which are missing in the Portal Implementation, are emptied. Other top level files and folders of the Portal Implementation are ignored (a warning is logged).
* The static files of the Portal Implementation are served in addition to the files in @static.path@. If both contain a file with the same path, the file of the Portal Implementation is served.
* The portal listens to Mesh events for nodes of the implementation schema in its project. Whenever the Portal Implementation is published, changed, moved or deleted
  (and after reconnecting to Mesh), the portal loads it again. The ZIP file is only extracted again, if its checksum changed.
  After an update, the cached queries are invalidated, so the new files are used without restarting the portal.
* If the Portal Implementation cannot be found, has no package, or loading it fails, the portal logs the problem and uses the existing local files.

NOTE: The files of the Portal Implementation must therefore be organized in the top level folders @templates/@, @queries/@, @i18n/@ and @static/@,
e.g. @templates/contentpage.hbs@ or @queries/loadByPath.graphql@.

NOTE: The portal loads the Portal Implementation from the default branch of the Mesh project.
