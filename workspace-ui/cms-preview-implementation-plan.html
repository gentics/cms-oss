CMS Preview: Recommendations and Implementation Plan

As of 2026-10-08 · Based on the spike (cms-preview-integration-spike.html)

The plan in short

Goal: while the AI writes a page, the user sees that page next to the chat, exactly as the CMS shows it.

  1. Ask first. We send our open questions to the GenAIx team and decide a few things in our own team. For example: the preview link GenAIx sends today opens the page for editing and locks it. It should only show the page.
  2. Show the page. The page appears in the right column. It reloads after every change the AI makes. A banner says when someone else is editing the page. A button publishes it. This step needs no other team.
  3. Select parts of the page. The user clicks a text or an image to select it. This waits until the CMS can tell us where each part sits on the page.
  4. Change a part with the AI. The user selects a part and says in the chat what should change. This waits until GenAIx can accept "this part of the page" in a message.
  5. Type directly in the page. This comes last, and only if users need it.
  6. Optional CMS changes. Only if the team agrees that the CMS may be changed for the Workspace.

Points to keep an eye on: If GenAIx does not add "this part of the page", users can still describe a part in words in the chat. If a proxy keeps the page from showing in the frame, the "Open" link next to it still opens the page. The customer's page scripts run next to the Workspace, so we want a short security check on that.

First we show the page read-only, because no other team has to do anything for that. Selecting parts of the page comes once we know the CMS can mark them. Changing a part with the AI comes once GenAIx can accept a reference to one part. Typing directly in the page comes last, when users need it.

Plan

Phase 0: Questions and decisions Can start

Runs alongside the other phases. Phases 2 to 5 need its answers.

Questions to the GenAIx team

  1. Can a chat message point to one part of one page (the page plus the part's name)? Phase 3 cannot start without this. Technical: a ContextReference for one tag (page + tag keyword).
  2. The preview link GenAIx sends today opens the page for editing and locks it. It should open the page read-only. Technical: today the link carries mode=view; read-only needs real=view.
  3. What does "discard" do in the CMS? And do unpublished changes to an already published page stay off the live website?
  4. Can GenAIx tell us for each part whether it is being worked on or has failed? Can the session snapshot hold a preview for each page instead of just one? Technical: the block status in page_structure.
  5. How should GenAIx learn that a user changed text by hand? For example, through a follow-up message that contains the new text word for word. Technical: as a verbatim part.

Decisions in our team

  1. May we change the CMS for the Workspace?
  2. May the Workspace save page content itself, or only through GenAIx?
  3. The customer's page scripts would run on the same host as the Workspace, without a sandbox. Is that acceptable?
  4. Product: locks apply to the whole page; hand edits start with a form; there is no Accept or Discard for each single AI suggestion.

Question to Ops: does a proxy in front of the CMS forbid showing the CMS in a frame? Technical: an X-Frame-Options or CSP header.

Phase 1: Show the page (read-only) In progress

No other team is needed. The right column is implemented on branch f-gpu-2712 (not merged yet): it appears as soon as GenAIx sends the first preview and shows the page read-only. Lock banner, Publish and a few extras are still open.

  1. Done Names for the data: the preview data from GenAIx has a name in our code. Technical: LivePreview in src/store/useWorkspaceEventStore.ts, taken from the generated preview.updated event type; no separate aliases were needed.
  2. Done Read the preview: GenAIx keeps the current preview for each session. The Workspace reads it from the session's updates and only holds it while it is shown. Technical: preview in useWorkspaceEventStore, set by each preview.updated.
    Open If GenAIx has shortened the session's update history, the preview only comes back with the next change. Reading it from the session snapshot would close that gap. Tabs for several pages are open too; we would track them ourselves, because GenAIx holds one preview per session. Technical: preview in GET /sessions/{session_id}/workflow, needed after 410 events_pruned.
  3. Done Frame address: GenAIx already sends it. The Workspace only makes sure it opens the page read-only. Technical: preview_url from preview.updated; mode=view and real=view are set when they are missing or different (readOnlyPreviewUrl in PreviewColumn.tsx).
  4. Done Preview column: the right column shows the page in a frame, with its address and an "Open" link. It appears as soon as the first preview arrives; before that there is no right column and no button for it. Technical: src/components/PreviewColumn/, passed to AppShell by SessionPage.tsx.
    Open Buttons for desktop, mobile (390 px) and full screen, and tabs for several pages.
  5. Done Reload: the frame reloads after each update, even when the address stays the same. Technical: the frame is keyed by the event's seq.
    Open Keeping the scroll position across a reload.
  6. Open Lock banner: ask the CMS whether the page is locked. Ask again after each update, and when GenAIx reports that the page is locked. Technical: a new function in cmsApiService, used through TanStack Query; GenAIx reports a lock with status 423.
  7. Open Publish: a Publish button. If GenAIx refuses because a quality check failed, show why. Technical: the publish transition; the refusal is 409 quality_gate_failed.

Done when: a session in which GenAIx writes a page shows that page read-only in the right column (done). The page reloads after each change (done), a banner shows locks (open), and the page can be published (open). Tests sit next to the code and all texts exist in English and German (done for the column). npm run check passes (fails today only on tailwind-boundary.test.ts, which also fails without this change). An end-to-end test covers the column (open).

Phase 2: Outline and select parts Waits for markers

The read-only page must mark its parts. Either the CMS feature COPY_TAGS does that, or the CMS is changed (phase 5).

What COPY_TAGS is: a CMS feature for copying content elements (tags) from one page to another. To recognise a copied element, the CMS writes markers into the page's HTML, and it does so in the read-only preview, the mode our frame uses. With these markers the Workspace can find each part of the page. The feature is off by default and is switched on for all nodes or per node. Switching it on also lets editors copy and paste tags, so it is a decision for whoever runs the CMS. As far as the code shows, only the page's own tags get markers, not the template's, and only tags with one outer HTML element (or localizable ones). How many parts a real page gets has not been checked yet. Technical: feature: copy_tags: true in conf/*.yml; markers data-gcn-pageid, data-gcn-tagid, data-gcn-tagname, data-gcn-i18n-constructname; added by AlohaRenderer.java:1511 in read-only mode. Docs: cms-oss-doc/src/main/source/feature_copy_tags.textile.

  1. Outlines: a layer above the frame draws an outline around each marked part. The outlines follow along when the user scrolls or resizes, and when the page reloads or changes. Technical: outlines from [data-gcn-tagid].
  2. Hover and select: only the innermost part under the mouse is highlighted. A click selects it and opens a menu with only the actions allowed for that part.
  3. States: a part can show that it is selected, that the AI changed it, or that it comes from the template. If GenAIx supports it, also that it is being worked on or has failed. Technical: changed from changed_elements; from the template via TEMPLATETAG / inherited.
  4. Focus mode: the rest of the page is covered, with a gap around the selected part.
  5. List of parts: next to the frame, a list of the page's parts lets keyboard users select them. Alt+Up and Alt+Down move to the outer or inner part. Technical: GET /rest/page/getTags/{id}.

Done when: parts can be selected with mouse and keyboard, the parts the AI changed are highlighted, and both work in the light and the dark theme. Until phase 3 is done, the user can only describe the selected part in words in the chat.

Phase 3: Change a part with the AI Blocked by GenAIx

GenAIx must accept a reference to one part (phase 0, question 1).

  1. Send the selection: the selected part is sent along with the chat message.
  2. Menu actions: "Change with AI" fills in the chat input. "Swap image" is answered by picking one of the options GenAIx offers. Technical: through a choice interaction.
  3. Hand edit form: a small form shows the part's text. On "Apply", the text goes to GenAIx together with the reference, and GenAIx writes it word for word. Technical: as a verbatim part.
  4. "Open in CMS editor": a button as a fallback. It needs no change from GenAIx, so it can be released earlier.

Done when: a user selects a part, asks for a change or types new text, and after the reload sees the change highlighted.

Phase 4: Type directly in the page Later

Needs a product decision. Editing text is medium effort; full CMS editing (content elements, images, files) would be large.

  1. Switching it on: "Edit by hand" can only be switched on while the AI is not working. If the AI is working, the user can stop it first. Technical: between run.started and run.completed.
  2. Connection to the CMS editor: the Workspace provides what the CMS editor expects from the page around it, and shows the editor's dialogs and menus with our own Dialog and DropdownMenu. Technical: GCMSUI_childIFrameInit with runPreLoadScript / runPostLoadScript, plus openDialog, openDynamicModal, openDynamicDropdown.
  3. Toolbar in our design: the editor's toolbar buttons are shown in our design, like the toolbar in the mockup. Technical: the components Aloha hands over through registerComponent.
  4. Apply or Cancel: "Apply" saves with the page's own save function inside the frame; "Cancel" drops the text. Afterwards the page is read-only again, and the chat notes that text was written by hand.
  5. Tell GenAIx about the hand edit, in the way agreed in phase 0.

Done when: a user types directly in the page with our toolbar, saves or cancels, and the AI continues afterwards without losing the hand edit.

Phase 5: CMS additions Optional

Only if the team decides that the CMS may be changed for the Workspace.

  • A read-only view of the page that marks each part, if COPY_TAGS does not fit. This unblocks phase 2.
  • A marker on each part whose content comes from a data source.
  • "Ask for the lock" and "Leave a note".
  • Discard that returns the page to its state from before the session, agreed with GenAIx.
