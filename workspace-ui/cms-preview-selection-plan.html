Selecting Parts of the Page, without Direct Editing

As of 2026-10-09

The Workspace shows the page the AI writes in a read-only preview next to the chat. This plan is about letting the user point at one part of that page, a text or an image, so the AI knows which part to change.

The plan in short

Starting point: typing directly in the page comes later. Until then the preview frame stays read-only all the time.

  1. Select from a list first. Next to the frame, a list shows the parts of the page. The user picks a part there. This needs nothing from the CMS that is not already there.
  2. Change the selected part with the AI. The selection from the list is enough for this. Until GenAIx can accept "this part of the page" directly, the Workspace names the part in the message text. That works today, as a stopgap.
  3. Outlines in the page come later. They need the CMS feature COPY_TAGS, or a CMS change. Once that is checked and switched on, the user can also select parts by clicking in the page.

Why the picture changes

To draw outlines, the Workspace must know where each part sits in the page. The CMS writes markers for that into the page's HTML, but not in every mode:

Frame modeMarkers for each partSide effect
Edit mode (direct editing)AlwaysThe page is locked for the user while it is open Technical: AlohaRenderer.java:1387-1500 annotates editable tags; AlohaPageServlet.java:198-206 locks the page.
Read-only (our frame)Only when COPY_TAGS is switched onNone for the page; switching the feature on also lets editors copy and paste tags Technical: AlohaRenderer.java:1511; the feature is off by default (Feature.java:45).

Edit mode cannot be used for the preview, because it would lock the page while the AI writes it. So as long as direct editing waits:

  • outlines in the page can only come from COPY_TAGS or a CMS change, and
  • selecting a part does not have to wait for outlines, because a list of the page's parts works without them.

Direct editing itself does not depend on COPY_TAGS: edit mode brings its own markers. Postponing it takes nothing away from the COPY_TAGS question.

Plan

Step 1: Select from the list of parts Can start

Needs nothing from other teams. Builds on the preview column that is already implemented.

  1. List of parts: next to the frame, a list of the page's parts, read from the CMS. Alt+Up and Alt+Down move to the outer or inner part. Technical: GET /rest/page/getTags/{id}, through a new function in cmsApiService and TanStack Query.
  2. Recognisable entries: names like content_3 mean nothing to users. Each entry shows the part's type (for example "Text" or "Image") and the start of its text. Until the outlines exist, this text is the only clue to where the part sits in the page, because the frame cannot scroll to it. To check: which of these fields getTags returns.
  3. Selecting: a click or Enter selects a part. The selection is shown in the list and stays until the user clears it or picks another part.
  4. Parts that cannot be changed: parts that come from the template are marked in the list, and "Change with AI" is not offered for them. To check: whether getTags lists template parts, and whether the agent can change them through the page.
  5. When a selection becomes invalid: an AI change can remove a part or add new ones. After each reload, the Workspace checks whether the selected part still exists. If it is gone, the selection is cleared and the user is told.
  6. Changed parts: after an AI change, the parts that changed are highlighted in the list. Technical: from changed_elements in preview.updated; that these names match the tag names is an assumption still to check.

Done when: a user can recognise and select a part from the list with mouse and keyboard, sees which parts the AI changed and which cannot be changed, and a removed part never stays selected. Until step 2, the user names the selected part in words in the chat.

Step 2: Change the selected part with the AI Can start (stopgap)

Needs nothing new from GenAIx. A chat message can already point at a whole page, but not at one part of it. So the Workspace sends the page as a reference and names the part in the text. The agent can find a part by its name and change it. Technical: ContextReference has type: page but no type for one tag (openapi.yaml, ContextReference); the part types of a message are a closed list (UserMessagePart). The agent finds a part with get_page_tags (searchable by tag name) and writes it with update_page_tags (mcp-tools.json).

  1. Send the selection: when a part is selected, the Workspace puts the page reference and the part's name in front of what the user typed. Technical: a reference part with ref.type: page, then a text part with the tag name; reference parts are already built in composerParts.ts and planMessage.ts.
  2. "Change with AI": fills in the chat input for the selected part.
  3. Language: the words the Workspace puts in front of the user's text ("part … (Text):") end up in the chat history. Like all texts, they exist in English and German and follow the user's language.
  4. While the AI waits for an answer (proposal): the chat input then answers the AI's question. The selection is not added to such an answer, because the AI asked about something specific. It stays and is used with the next normal message. Technical: answers go out with replyTo (SessionPage.tsx).
  5. When someone else has locked the page (proposal): "Change with AI" is disabled, and the Workspace says who holds the lock. To check: where the Workspace learns about the lock, and how GenAIx reports a write that failed because of one.

Example

  1. The AI wrote the page "Neue Nutzungsbedingungen ab Q3". The user selects the part content_3 (a text) in the list next to the frame.
  2. The user types "make this shorter" and sends it.
  3. The Workspace sends this message to GenAIx: 
    POST /sessions/{session_id}/messages
{
  "parts": [
    { "type": "reference",
      "ref": { "type": "page", "id": "9142", "node_id": 3,
               "label": "Neue Nutzungsbedingungen ab Q3" } },
    { "type": "text", "text": " – part \"content_3\" (Text): " },
    { "type": "text", "text": "make this shorter" }
  ]
}
    In the chat history it reads: @[Neue Nutzungsbedingungen ab Q3] – part "content_3" (Text): make this shorter.
  4. GenAIx loads the page and hands it to the agent. The agent looks up content_3 by name and writes the shorter text into it.
  5. GenAIx reports the change. The preview reloads, and content_3 is highlighted as changed in the list. Technical: preview.updated with changed_elements: ["content_3"].

Steps 4 and 5 are what we expect, not what GenAIx guarantees: the agent has to read the part's name from the text. How reliably it picks the right part can only be tested with the real GenAIx; the mock replays fixed answers. That changed_elements uses the same names as the list is also still to check. Page ID 9142 and the page title are the examples from the GenAIx contract.

Is the stopgap good enough? Before relying on it, we test it with the real GenAIx: about 10 to 20 requests on a real page, each naming one part, and we count how often the agent changes exactly that part. We agree beforehand which share is enough. If the result is below that, step 2 waits for the proper reference from GenAIx after all.

Later, the proper way: we keep asking the GenAIx team for a reference to one part. Once it exists, only the message changes: instead of the part's name in the text, the reference itself points at the part. The list, the selection and "Change with AI" stay the same. Technical: a ContextReference for one tag (page + tag keyword).

Done when: a user selects a part in the list, asks for a change, and after the reload sees that part highlighted as changed.

Step 3: Outlines in the page Waits for COPY_TAGS and same origin

Needs two things: COPY_TAGS switched on for the node (or a change to the CMS that adds markers in read-only mode), and the page in the frame coming from the same origin as the Workspace.

Why the same origin matters: a browser only lets a page look into a frame when both come from the same origin, meaning the same protocol, host and port. Otherwise the Workspace cannot find the marked parts in the frame, and no outlines are possible, whatever COPY_TAGS does. The GenAIx contract only asks for "same-site", which is less than that. Technical: openapi.yaml, Preview.preview_url: "a client that embeds it must be same-site with the CMS".

  • Local development: today the dev server forwards only the GenAIx and REST calls to the CMS, not the preview page. A preview link to the CMS host is then a different origin, so the outlines cannot work locally yet. Technical: vite.config.ts proxies /rest/proxy/genaix/ and /rest, not /alohapage.
  • Production: it works if the Workspace is served from the CMS host itself. This repository does not show whether it is.
  1. Check the origin: find out whether the Workspace is served from the same origin as the CMS in production. Forward the preview page in the dev server too, so the outlines can be tried locally. Technical: add /alohapage to the dev proxy; the preview link must then point at the Workspace's own host.
  2. Check COPY_TAGS: switch it on in a test CMS and count how many parts of a real page get markers. Technical: feature: copy_tags: true in conf/*.yml; count [data-gcn-tagid] in the frame.
  3. Decide: whoever runs the CMS decides whether the feature may be switched on, since it also enables copy and paste of tags for editors.
  4. Outlines: a layer above the frame draws an outline around each marked part. The outlines follow along when the user scrolls or resizes, and when the page reloads or changes. The customer's page itself is never changed. Technical: outlines from [data-gcn-tagid].
  5. Click to select: only the innermost part under the mouse is highlighted; a click selects it. Selecting in the page and in the list stay in sync.

Done when: parts can also be selected by clicking in the page, in the light and the dark theme.

Based on reading the CMS code (AlohaRenderer.java, AlohaPageServlet.java, Feature.java) and the CMS docs (cms-oss-doc/src/main/source/feature_copy_tags.textile). Nothing was tried on a live CMS.
