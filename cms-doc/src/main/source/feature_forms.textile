h2. Gentics CMS Forms

With the feature _forms_ it is possible to manage forms in Gentics CMS.
* Forms are created and edited in the Editor User Interface.
* Forms can be included into pages.
* Forms can be published into Mesh ContentRepositories (Gentics Mesh Forms Plugin is required).
* Forms are rendered on the client side by *FormGen*.

NOTE: See the "Forms Migration Guide":forms_migration.html when updating from an older CMP Version (<= CMP 8.4).

endprologue.

h3. Configuration

In order to use the feature, it must be activated in the configuration:

<shell filename="conf/features.yml">
feature:
	forms: true
</shell>

Each form is based on a form type, which must also be configured.
For each of these types, a list of available form elements and their settings must be created.

Elements in the context of forms are defined as things an editor can place into the form. These come in two types: *Controls* and *Blocks*.

Controls are Elements, the frontend user can interact with and which stores/handles form data.
Blocks on the other hand are only for visual extras to the form, such as extra description texts or grouping of elements.

h4. General configuration

The general configuration for the forms is defined the following way:

<shell filename="conf/forms.yml">
forms:
  formGenTranslations:
    form_loading:
      en: "Loading ..."
    custom_key:
      en: "Example"
  types:
    generic:
      nameI18n:
        en: Generic Type
      # See below for all options
    otherType:
      nameI18n:
        en: Another Type
</shell>

h5. Internal and external forms

Forms come in two kinds, *internal* and *external*, which are handled differently. Which kind a form is, is determined by its form type and configured per form type via the +external+ flag (in combination with +pluginName+) in the General configuration above.

|_. Kind |_. Configuration |_. Handled by |
| *Internal form* | +external: false+ (the default when the flag is omitted) | A Gentics Mesh plugin, named by +pluginName+ (e.g. the Gentics Mesh Forms Plugin for +pluginName: "forms"+), which processes and stores the submissions. |
| *External form* | +external: true+ | Treated as an external form and *not* by the Gentics Mesh Forms Plugin. Editing forms is restricted and only allows editors to add block elements. |

*Internal forms* are the forms managed by this feature: they are created and edited in the Editor and their submissions are processed by the configured Mesh plugin. This is the default, and all examples in this document are internal form types.

NOTE: The +external+ flag is a property of the form *type*, not of an individual form. All forms created from a form type therefore share the same kind.

h5. Captchas

Each option is defined by a +value+ (the identifier stored on the form) and a localized +labelI18n+.

|_. Value |_. Label (en) |_. Label (de) |_. Description |
| +recaptcha_checkbox+ | Recaptcha: Checkbox | Recaptcha: Häckchen | Google reCAPTCHA rendered as an explicit "I'm not a robot" checkbox |
| +recaptcha_invisible+ | Recaptcha: Background | Recaptcha: Hintergrund | Google reCAPTCHA that runs invisibly in the background (no checkbox) |
| +friendly_auto+ | Friendly Captcha | Friendly Captcha | Friendly Captcha that starts its verification automatically |
| +friendly_button+ | Friendly Captcha: Button | Friendly Captcha: Button | Friendly Captcha triggered via a button |
| +friendly_background+ | Friendly Captcha: Background | Friendly Captcha: Hintergrund | Friendly Captcha that runs in the background |

IMPORTANT: +captchaOptions+ only selects *which* captcha variant is used. The provider credentials and endpoints themselves — e.g. the reCAPTCHA / Friendly Captcha *site key*, *secret / verification key* and the verification URL — are *not* part of the form configuration. They must be configured in the forms plugin configuration (+config.yml+ of the forms plugin), the same place where e.g. the +binary+ +allowedTypes+ are defined.

h6. +string+ control

|_. Setting |_. type |_. backend |_. propertyPath |_. Description |
| +defaultValue+ | string | true | — | Default value |
| +maxLength+ | number | true | +validation.maxLength+ | Maximum number of allowed characters |
| +validation+ | select | true | +validation.regexValidation+ | Validators based on regular expressions with error messages. The value has to be a validation object, see the table below for more info. |
| +numberOfLines+ | number | false | — | Number of lines (renders the input as a multiline text field) |

The Validation object has the following properties

|_. Property |_. type |_. Description |
| +key+ | string | Acts as an ID between the various validation options |
| +regex+ | string | A *java* regex string to validate against |
| +errorMessage+ | translation object | The error message for the frontend user |

Example:

<shell filename="conf/forms.yml">
forms:
  types:
    example:
      controls:
        string:
          labelI18n:
            de: String Beispiel
            en: String example
          settings:
            - id: defaultValue
              type: string
              labelI18n:
                de: Standardbefüllung
                en: Default value
              backend: true
            - id: maxLength
              type: number
              labelI18n:
                de: Maximallänge
                en: Maximum Length
              backend: true
              propertyPath: validation.maxLength
            - id: validation
              type: select
              labelI18n:
                de: Validierung
                en: Validation
              backend: true
              propertyPath: validation.regexValidation
              options:
                - value:
                    key: "email"
                    regex: "^(([^<>()\\[\\]\\\\.,;:\\s@\"]+(\\.[^<>()\\[\\]\\\\.,;:\\\
                      s@\"]+)*)|(\".+\"))@((\\[[0-9]{1,3}\\.[0-9]{1,3}\\.[0-9]{1,3}\\\
                      .[0-9]{1,3}])|(([a-zA-Z\\-0-9]+\\.)+[a-zA-Z]{2,}))$"
                    errorMessage:
                      de: "Das soll ne eMail Adresse sein?"
                  labelI18n:
                    de: "E-Mail"
                    en: "Mail"
</shell>

h6. +adminmail+ control

Element to specify which admin mail addresses submission notifications should be sent to. If such an element is present in the form, the form's +email+ property is ignored, and the recipients are instead taken from the selected option keys (which are mapped to the configured mail addresses). When no +adminmail+ element is present, mail sending falls back to the admin email configured on the form (+email+).

|_. Setting |_. type |_. backend |_. propertyPath |_. Description |
| +selectOptions+ | options | true | — | List of selectable key/value pairs |

h6. +aggregate+ control

An special element which creates a sub-form, where multiple entries can be created/submitted, aggregated under one common name.

An example would be, a list of attendees for an event, where each attendee has and input for +firstName+, +lastName+, and +email+. The aggregate would hold info for the three controls, but these can be entered *n* times, and the reports receives a single list value with all the attendees.

|_. Setting |_. type |_. backend |_. propertyPath |_. Description |
| +showFilter+ | boolean | false | none | If the aggregation table should add a filter input, where displayed elements are filtered by the input's content. |
| +showOnlyFirstLine+ | boolean | false | none | If true, then each element is displayed as individual collapsible. Only the first element is always displayed, even when collapsed. |
| +buttonDisplayStyle+ | select | false | none | How the buttons for adding/editing/removing elements should be displayed. Possible option-values: +icon+, +text+, +icontext+ |

h6. +lazyCatalog+ control

Special +catalog+ component, which primarily works the same. The main difference is where it loads the options from.
This is mainly used for conditional options, where the evaluation for these options is handled in the backend, so no special configuration is required here. For all catalog settings, see the regular +catalog+ control.

h6. +reference+ control

Special +catalog+ component, which requires a search input, and the options are searched in the backend. Options are references to elements within Acta-Nova, the user has access to.

For all catalog settings, see the regular +catalog+ control.

h6. +spacer+ block

Simply an empty block, used to create space between elements.

h6. +group+ block

A simple container element, which groups elements together. If the group has a display condition which isn't met, all child-elements won't be rendered either.
This can be used to manage element conditions in a more central way, Instead of having to set the condition on each element individually.

h6. +text+ block

A simple block element which renders the text content which was entered.

|_. Setting |_. type |_. Description |
| +text+ or +value+ | string or translation | The text that should be rendered. May be simple text or HTML (use `richContent: true`). |

h6. +conditionalcontainer+ block

Deprecated: The same as +group+, just here for compatibility reasons. Use +group+ if possible.

h6. +sectionheadline+ block

Mainly the same as +text+, except that the text content is always escaped (i.E. no richContent), and put in a +<h2>+ element.

Deprecated: Use the +text+ block instead with custom formatting.

A setting is simply a property of the element, which an editor can change.
Settings are defined on each element configuration individually and can be configured to your projects needs.

The following setting types are available

|_. Type |_. Value |_. Description |
| +string+ | string | Depending on the configuration, a simple text input, a textarea, or a rich-content input via aloha editor. |
| +translation+ | translation object | Similar to +string+, but each language may have a different string content. |
| +number+ | number (float) | Accepts any numeric value including decimals. |
| +integer+ | number (integer) | Accepts whole numbers only. |
| +boolean+ | boolean | A checkbox that yields +true+ or +false+. |

| +select+ | string (one of options) | A dropdown with a fixed list of options defined in the configuration. Set +multiple: true+ to allow selecting more than one value. |

Each setting has the following properties:

|_. Property |_. Type |_. Required |_. Description |

h4. Setting conditions

Settings may not always be relevant, and can be hidden with conditions. Only when a condition resolves to +true+, the setting may be displayed.
Conditions are identified by their unique property key, to make writing/reading them as straight forward as possible.

Conditions are separated into two groups:

* Modifier Condition
* Source Condition

Modifier conditions are the three basic operations +or+, +and+, and +not+.
Meanwhile, source conditions require a source element, from where the value is get and to match the actions against.

The list of source conditions and a description on how to use them:

|_. Condition |_. Needs source |_. Value Type |_. Description |
| +or+ | false | list of conditions | Evaluates to true, if any of the provided conditions are true |
| +and+ | false | list of conditions | Evaluates to true, only if all provided conditions are true |
| +not+ | false | condition | Evaluates to true, if the provided condition is false |
| +equals+ | true | anything |If the source value equals exactly the provided value. |
| +matches+ | true | string | If the source value matches the provided regex string. |
| +contains+ | true | anything | If the source value (has to be a list) contains the provided value. |
| +includedIn+ | true | list of anything | If the source value is contained within the provided list. |
| +biggerThan+ | true | number | If the source value is bigger than the provided value. |
| +lowerThan+ | true | number | If the source value is lower than the provided value. |
| +empty+ | true | boolean | Checks if the source value is empty, and then checks if the provided value is the same. |
| +visible+ | true | boolean | Checks if the source value (usually a control source) is visible, and then checks if the provided value is the same. |
| +disabled+ | true | boolean | Checks if the source value (usually a schema source) is disabled, and checks if the provided value is the same. |

h5. Source Types

Sources are also defined by the unique key, and work the following way

|_. Type |_. Description |
| +setting+ | ID of the setting, which manages the value. Will check the settings +backend+ and +propertyPath+ to get the element value. |
| +schema+ | JSON path to the property in the schema of the element. Only works in +control+ elements. |
| +control+ | ID of another control within the form to load/check against. |

h5. Conditions Example

<shell>
condition:
  and:
    - not:
        equals: true
        source:
          setting: foobar1
    - or:
      - empty: true
        source:
          control: otherSetting
      - biggerThan: 15
        source:
          control: attendeeCount
</shell>

h4. Form flows

A form flow controls the sequence of screens a user is guided through when filling out a form — for example the form itself, an optional summary, and a final success screen. Each form type defines its flows in the +flows+ list of the General configuration; the first entry is used as the default. A flow determines which screens are shown, which buttons appear on each screen, and which additional variables are passed to the screen components.

This allows the form process to be tailored to a project's needs, for example:

* Show or hide individual buttons (such as a print button on the summary screen).
* Pass variables that enable additional behaviour in a screen (such as showing detailed information in the summary).
* Add or remove screens, for example by inserting a summary step before submission.

The example configuration below defines two flows for the +generic+ type: a +default+ flow leading straight from the form to the success screen, and a +with_summary+ flow that inserts a summary screen in between.

A flow has the following top-level fields:

|_. Field |_. Type |_. Required |_. Description |
| +id+ | string | required | Unique identifier of the flow. Used to reference the flow from a form. |
| +labelI18n+ | translation map | required | Human-readable name of the flow, keyed by language code. |
| +nameTranslationKey+ | string | optional | Translation key for the flow name. |
| +steps+ | list of step configs | required | The ordered sequence of screens the user is guided through. See the step fields below. |

Each entry in +steps+ describes a single screen:

|_. Field |_. Type |_. Required |_. Description |
| +reactClass+ | string | required | The screen component to render, e.g. +FormScreen+, +SummaryScreen+ or +SuccessScreen+. The available components are provided by FormGen. |
| +buttonLabelTranslationKey+ | string | optional | Translation key for the label of the button on the preceding screen that navigates to this step. |
| +nameTranslationKey+ | string | optional | Translation key for the screen title. |
| +descriptionTranslationKey+ | string | optional | Translation key for the screen description. |
| +buttons+ | list of button configs | optional | The navigation buttons shown in the screen footer. See the button fields below. |
| +variables+ | list of key-value pairs | optional | Additional values passed to the screen component as properties. Each entry has a +name+ and a +value+ (e.g. +showDetails: true+ to let the summary screen show detailed information). |

Each entry in +buttons+ describes a single footer button:

|_. Field |_. Type |_. Required |_. Description |
| +reactClass+ | string | required | The button component to render, e.g. +SubmitButton+, +CancelButton+, +PreviousPageButton+, +NextPageButton+, +PrintPdfButton+ or +DetailInfoButton+. The available components are provided by FormGen. |
| +labelTranslationKey+ | string | optional | Translation key for the button label. |
| +mobileDisabled+ | boolean | optional | If +true+, the button is hidden on mobile devices (where the button component supports it). |

NOTE: The screen and button components available as +reactClass+ values are provided by *FormGen* and can be extended per project. For configuring and customizing these components see the "FormGen Customizing Guide":formgen.html.

NOTE: Assign at least one language to the node where you will be creating forms.

After this, the forms feature must be enabled for every node that should contain forms. Enable it per node in the *Node Management* tab of the administration interface, under the node's *Features*.

Once the feature is enabled for a node, an additional *Form Types* tab appears for that node. Use it to assign the form types that should be available when creating forms in that node.

h3. Translations

Translations can be managed in two ways: Globally or per Type.
Usually all common translations are managed globally, and if a type has some additional translations, then these are added per type.

Configuration for these is quite simple: Create a property `formGenTranslations` under `forms` for a global configuration, and `formGenTranslations` under `forms.types.<type>` for a type specific one.

Each key under the `formGenTranslations` property is then the translation key, and has a translation object as a default value. The translations themself are managed via a custom tool in the CMS.

Example:

<shell filename="conf/forms.yml">
forms:
  formGenTranslations:
    global_translation_key_1:
      de: Beispiel 1
      en: Example 1
    global_translation_key_2:
      de: Beispiel 2
      en: Example 2
  types:
    generic:
      formGenTranslations:
        generic_type_translation_key_1:
          de: Typen specifische übersetzung 1
          en: Type specific translation 1
</shell>

h3. Redirect After Submission (successUrl)

A successUrl can be configured in the form properties to specify the page the user should be navigated to after successfully submitting a form.

h4. Default Behavior

Because flows are individually configurable and an automatic redirect would restrict the flow execution, the navigation does not happen automatically. Instead, a button is displayed on the success screen whenever a successUrl is configured. The user must actively trigger the redirect by clicking the button.

This behavior is built into the default flow and requires no additional implementation.

h4. Behavior With Customized Flows

If the flow is overridden or extended for a specific project, the default behavior no longer applies. In this case, the redirect logic must be implemented explicitly. Two options are available:

* *Custom Elements:* The logic for evaluating the successUrl and triggering the navigation is implemented directly within the custom element.
* *Hook postSubmitForm:* The redirect is handled via the postSubmitForm hook, which is called after the form has been submitted successfully.

In both cases, ensure that the successUrl is read from the form data and that the navigation is executed at the correct point in the flow.

NOTE: The redirect handling for customized flows — custom elements or the +postSubmitForm+ hook — is implemented and configured in *FormGen* (see the "FormGen Customizing Guide":formgen.html).
